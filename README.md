# 重力镜头实验室 · Gravity Lens

异向重力场景下的摄像机姿态控制器。镜头局部上方向由**当前有效重力/表面法线实时计算**，
不把世界坐标的 +Y 当成所有区域的默认答案。场景是真实三维几何（星球曲面、重力舱墙壁、
斜面、天花板），不是旋转天空盒。

> **图形入口（主入口）**
> `npm install` 后执行 `npm run dev`，浏览器打开 **http://localhost:5173**。
> 页面顶部有三个页签：**星球表面 / 重力舱 / 输入轨迹**。
> 命令行只是这套解算器的辅助批量接口（见文末），日常观察与异常提示都在网页里。
>
> 右侧结果栏新增 **姿态更新成本 · 姿态缓存** 两项，以及**相机姿态与视野连续**、
> **重力镜头** 两条运行状态条：正常/回退/异常会直接标在页面里，不需要看控制台。

## 2. 重力镜头图形入口怎么用

| 页签 | 作用 | 关键操作 |
| --- | --- | --- |
| **星球表面** | 在半径 40 的球面上行走，重力 = 表面外法线 | `W A S D` 沿球面行走；拖拽改变局部偏航/俯仰；滚轮缩放臂长 |
| **重力舱** | 地板 / 天花板 / 四面墙 / 35° 斜面共 6 个真实表面 | 左侧「重力方向」按钮切换有效重力，镜头立即按新法线重新计算上方向 |
| **输入轨迹** | 播放内置测试轨迹并给出逐帧判定 | 选择轨迹 → 播放；右侧「轨迹判定」显示 6 项检查是否通过 |

右侧结果栏全部来自**真实解算输出**，不是写死的演示数字：

- **相机姿态**：Forward / Up / Right 基向量、四元数、局部偏航、局部俯仰、当前重力上方向、
  水平线求解模式（`cross` / `blend` / `transport`）。
- **视野连续性（逐帧）**：正交误差、地平线滚转、单帧姿态跳变、视锥重叠率，并绘制历史曲线。
  下方还有两项**实测**读数：
  - **姿态更新成本**：在真实解算器上批量计时得到的 µs/次求解（间隔 0.5 s 重测）。
    单帧求解远低于浏览器 `performance.now()` 的 ~0.1 ms 分辨率，所以按批次计时
    （384 步/批 × 2 批，取更快的一批），再对最近 6 次取**滚动最小值**以排除调度抖动；
    测不出来时保留上一次读数，不会把 0 当成成本。**注意**：这个实时读数在演示里重力方向
    基本不变，走的是缓存命中路径，因此只反映“界面此刻的更新开销”，
    **不能**与 §6.4 的基准加速比直接比较（基准强制每帧改变重力，走完整解算路径）。
  - **姿态缓存**：精确输入缓存命中/实际求解次数。
  - **相机姿态与视野连续**状态条：正常 / 回退（`POLE_FALLBACK`）/ 异常（`ROLL`、`ORTHO`、
    `STEP`、`FOV`、`NON_FINITE`）直接标出对应异常码与指标。
- **重力镜头**：把当前局部上方向与局部地平线投影到屏幕，直观显示镜头相对地平线的姿态；
  下方状态条区分「局部上方向可见」「接近极点但仍在 cross 带」「退化带 blend」「正对上方向
  transport」四种运行状态，并给出仰角、`|f×u|`、当前滚转。
- **异常提示**：`POLE_FALLBACK`（极点回退）、`ROLL`、`ORTHO`、`STEP`、`FOV`、`NON_FINITE`
  会以浮层提示，并和结果栏同一份数据联动。

切换重力按钮、拖动「允许俯仰穿过极点」、调整 FOV 时，结果栏与曲线会立刻反映新的解算结果。

## 3. 控制器语义

### 3.1 局部坐标系

每一帧由当前有效重力给出局部上方向：

```
up   = normalize(-gravity)          // 或直接是表面法线
```

- **偏航（yaw）**：绕局部上方向旋转的航向角，切平面内左右转向。
- **俯仰（pitch）**：朝局部上方向 / 背离它抬起或下压视线，0° 为水平。
- **相机基**：`forward`、`right`、`up` 由航向、俯仰与局部上方向构造，再经正交化
  （`src/core/rig.js` 的 `compute()` / `solveHorizon()`）。
- 相机四元数由正交基经 `makeBasis(right, up, -forward)` 得到，与基向量严格一致。

由于上方向来自重力而非世界 Y，在墙壁、天花板、斜面上镜头都会把所在表面当作「地面」，
world-up 只在重力恰好等于 +Y 时才成立。

### 3.2 极点奇异性与连续回退

地平线通常由 `right = normalize(cross(forward, up))` 给出。当视线接近局部上方向时
`|cross| → 0`，方向由舍入噪声决定，**直接归一化近零向量会产生随机翻转**。

处理策略（`solveHorizon()`）：

1. **有向叉乘**：`s = |forward × up|`。
   - `s ≥ 1e-3` → `cross` 模式，使用叉乘方向，并与上一帧的右向量做**逐帧符号对账**
     （`horizonParity`），把越过极点时的符号翻转变成连续旋转，而不是 180° 跳变。
   - `1e-4 ≤ s < 1e-3` → `blend` 模式，在上一帧携带的切向与叉乘方向之间按 smoothstep 连续混合。
   - `s < 1e-4` → `transport` 模式，完全由上一帧的切向参考系（最小旋转携带）确定地平线；
     **不对近零叉乘做归一化**。
2. 若连携带参考系都不可用（首帧或重力瞬变后），回退到由重力构造的稳定切向参考。
3. 每帧右向量都会重新投影到与 forward 垂直的平面上再归一化，up 由 `right × forward` 得到，
   保证基正交。

极点驻留（视线正对上方向并持续偏航）时，`transport` 模式让画面继续平滑旋转而不会随机翻转；
离开极点时叉乘方向重新接管，产生一次**有界**的姿态修正（本仓库测得最大 3.611°，阈值 25°，
视锥重叠 98%，判定通过）。

### 3.3 重力切换（建模的不连续）

`switchGravity(newUp)` 用于 180° 这类**设计上的**重力突变：它会先清空携带的参考系，
再按新重力一次性求解，并记录一条 `discontinuity`（`GRAVITY_SWITCH`，含角度与说明）。
这保证姿态跳变只出现在显式建模的切换点上，其它帧之间保持连续。
界面上的重力按钮走的就是这条路径。

### 3.4 角色朝向解耦

角色模型朝向是一条独立的**表面方位**（`characterYawVec`），只驱动模型旋转与行走方向，
不进入镜头地平线解算。角色的上下起伏、左右摆动等动画**不会**传导到整个视图。
结果栏「角色」分组可单独旋转 15° 验证：相机四元数不变。

## 6. 姿态更新优化

### 6.1 冻结基准

`src/core/rigBaseline.js` 是**优化前的解算器原样副本**，只供基准与对照测试导入，
应用与轨迹回放都不使用它。基准测试与一致性测试都**真实执行**这个模块，不存快照、
不伪造结果；任何姿态差异都会同时反映在 `artifacts/pose-bench.json` 与
`tests/pose-parity.test.js` 里。

### 6.2 成本分解（实测，移动重力全路径）

`npm run bench` 在同一进程内交替运行两个解算器，每项计时分多轮取样后取中位数（不是按源码行数估算）。
本机是共享机器（10 vCPU，跑基准时 loadavg ≈ 4.6），所以下表是**实测量级**，同一份
`artifacts/pose-bench.json` 还记录了每轮的中位数区间作为噪声带：

| 阶段 | 耗时 | 占整步 |
| --- | --- | --- |
| **整步 `rig.step()`** | ~2–3.5 µs（轮间 2.0–3.3 µs） | 100% |
| 姿态几何解算 `_solveGeometry`（heading/forward/地平线/四元数/指标） | ~0.7–1.0 µs | 30–45% |
| 视锥重叠 `frustumOverlap` | ~0.17 µs | ~8% |
| 异常扫描 `detectAnomalies` | ~0.02 µs | ~1% |
| 姿态记录 + 历史环形缓冲 | 余量 | ~45–65% |

> 占比小的原因是缓存命中路径把几何解算压到了 ~0.8 µs，剩下的固定开销（帧记录、历史缓冲、
> 异常对象）在整步里占比随之变大；这是优化后真实的结构，不是把成本挪到了“余量”里。

### 6.3 改了什么，为什么这样排序

`compute()` 被拆成 `_solveGeometry(U)`（纯几何，无指标副作用）+ 指标/指标记录部分。
几何解算的计算顺序与依赖关系：

1. **heading**：偏航在**当前重力切平面**内用 `refForward/refRight` 旋转，所以任何重力下都有定义。
2. **forward**：由切平面基 + 重力上方向 + 俯仰直接合成，避免 ±90° 俯仰时零化 heading。
3. **horizon**：必须在 forward 之后，因为退化判据就是 `|forward × up|`；well-conditioned 走
   `cross`，否则用上一帧 tangent 走 `blend`/`transport`。
4. **quat**：由已解出的 `right/up/forward` 建基。
5. **metrics**：正交误差、重力滚转、地平线反号全部读最终基，所以放最后。

在这之上加 **精确输入缓存**：只在 `basisVersion`（重力基重建次数）+ 精确 `yaw`/`pitch` +
上一帧 `prevRight` **逐位相等**时复用几何结果。任何重力或视角变化——哪怕一个 ulp——都走完整解算，
所以**微小旋转照常逐帧累积**，极点退化分支（`cross/blend/transport`）从不被缓存跳过。

### 6.4 各载荷结果（同一进程、交替计时、多轮中位数）

| 载荷 | 基线 | 优化后 | 加速（轮间区间） | 角误差 | 更新成本 |
| --- | --- | --- | --- | --- | --- |
| `slow-gravity` 缓慢转重力 | 3.7–4.7 µs | 2.2–2.7 µs | **~1.7–2.0×**（1.25–2.34×） | 0 | 0 |
| `reversed-axis` 反向轴（近极点退化带） | 3.7–4.5 µs | 2.2–2.6 µs | **~1.6–2.1×**（1.14–2.57×） | 0 | 0 |
| `slow-gravity-idle-look` 重力转、视角不动 | 3.5–4.1 µs | 2.0–2.7 µs | **~1.3–1.7×**（1.18–2.06×） | 0 | 0 |
| `idle` 输入完全不变 | 3.3–4.1 µs | 0.5–0.7 µs | **~6–7×**（5.5–7.4×，命中缓存） | 0 | 0 |

「角误差」对两列都是同一趟运行里的 `|优化 - 基线|`：单帧跳变、正交误差、最终姿态四元数差均
**逐位为 0**，本机所有载荷/轮次组合无一例外。括号里是**多次重复运行**观测到的轮间中位数区间；
`artifacts/pose-bench.json` 只记录生成它的那一趟（含该趟的区间与本机负载）。单轮偶发尖峰
（例如共享机器上的调度抖动）会被区间如实暴露，而不会被四舍五入的“平均加速”掩盖。

### 6.5 复核范围与有意的取舍

- 只改姿态更新：`solveHorizon` 的退化判定、阈值、符号对账、携带逻辑**一字未动**；
  `applyUp` 的 Rodrigues 旋转与反向轴 180° 分支保持原样（只多了一次“重建后是否真的变了”的
  逐位比较来决定是否失效缓存）。
- `frustumOverlap` 用**代数等价**方式去掉逐样本 `normalize`（投影比值对正比例因子不变），
  5000 组随机位姿与旧实现比对**逐位相等**；不是放宽容差。
- 若角误差或更新成本之外的任何行为退化，就撤回对应优化：目前已核对
  `npm test`（含逐帧基线对照）、6 条轨迹数值、网页内切换重力/角色旋转/轨迹回放，
  均无退化。

### 6.6 运行参照

- `npm run bench` / `node bench/pose-bench.mjs --save --json`：无浏览器数值参照。
- `artifacts/pose-bench.json`：加速比、角误差、成本分解的可提交记录。
- `tests/pose-parity.test.js`：六条轨迹逐帧、逐指标与冻结基线**全等**的回归门槛。

## 8. 单元测试覆盖

`npm test`（25 项）覆盖：逐帧正交性与四元数一致性、上方向确实来自重力（非世界 Y）、
零滚转、球面/墙面连续、重力切换时的方位携带、建模翻转的不连续、极点回退连续性、

**朴素 `normalize(cross(f,u))` 实现与本品对照（朴素 >90° 跳变，本品 <10°）**、
6 种重力预设下的偏航/俯仰语义、翻转后的屏幕相对偏航、角色朝向/模型抖动无法改变相机四元数、
全部轨迹通过验收，以及视锥重叠度 1.0（相同）/ 0.0（相反）的边界。

新增 4 项姿态优化对照（`tests/pose-parity.test.js`）：6 条轨迹**逐帧**与冻结基线比较
forward/up/right/四元数**逐位相等**；逐帧比较跳变、滚转、正交、视锥重叠、异常码全等；
极点驻留轨迹的 `sinHorizon`/`blendWeight` 全等（退化带未被缓存跳过）；以及“完全相同输入
允许命中、单个 ulp 重力变化必须重新求解”的缓存边界。
